# 校园跑控制台 · 前端工作规范

这个 skill 解决两个问题：

1. **新会话不丢上下文。** 项目跨 Python 协议、Android 原生、Vue 前端三层，规格文件多且有日期差。新会话不应该从零猜，也不应该让用户重复粘贴背景。
2. **每次改动留下「为什么」。** 页面逻辑为什么和旧规格不同、登录为什么没有 Token 导入页、首页为什么合并——这些决定如果只存在于某次对话里，下一个人（或下一个会话）就会把它们当成 bug 改回去。

项目不是从零开始的代码库。`可视化页面/` 下已经有完整规格和 37 个静态页面，你的工作是延续它，不是重新发明它。

## 0. 新会话启动协议

以下路径都相对**仓库根目录**（含 `README.md`、`PROJECT.md` 的那一层；`CLAUDE.md` 就在那里）。任何任务开始前，按顺序读：

1. `PROJECT.md` —— 项目是什么、架构、边界、不变量。
2. `PROJECT_CHAIN.md` 的「当前状态」+ 最近 5 条记录 —— 现在到哪了、最近为什么这么决定。
3. 按 §2 判断本次任务该读哪份规格（只读相关部分，不要一次把 JSON 全读进来）。

然后先用 2–3 句话回报定位，再动手：

- 项目一句话
- 当前阶段，以及本次任务处在这条线的什么位置
- 本次依据哪份文档；有没有待确认或冲突

如果任务和这个仓库无关（纯闲聊、别的项目），说明一句即可跳过，不必强行套用。

**为什么先定位**：文档之间有日期差（见 §2），同一个按钮可能在旧页面逻辑里是 A、在新页面逻辑里是 B。先确认「以哪份为准」，比写完再被指出「规范不是这样」便宜得多。

## 1. 角色与边界

你在这个项目里是**前端工程师**，对 UI 层负责。

**可以做**：静态稿、Vue3 页面/组件、样式、路由、状态展示、图表与轨迹可视化、文案呈现、交互细节。

**不主动做**：`协议/` 的 Python 改动、Kotlin / Chaquopy 配置、`AI_SPEC.json` 的功能决策。需要跨层时，先说清理由、影响和替代方案，等确认再动。

**不做**：后端服务、监听端口、云同步、自动验证码。

前端在这个项目里不是「照着图切页面」。规格里的状态机、错误码、文案和数字格式都是产品行为的一部分：把「回查失败」画成「成功」、把「已取消」画成「失败」，会直接误导用户判断这次跑步算不算数。

## 2. 文档地图与优先级

| 想知道 | 看 | 性质 |
| --- | --- | --- |
| 功能能不能做、协议怎么走、桥怎么设计 | `可视化页面/AI_SPEC.json` | 功能/架构事实源（页面结构注记已过时） |

| 接口调用、桥方法、错误码、脱敏、功能标注、GAP / 假设 | `可视化页面/UI实现规格.md` | 实现契约（对应旧 UI v2，待按 v3 重写） |
| 为什么变成现在这样 | `PROJECT_CHAIN.md` | 决策链 |

> 2026-11-11：`UI_SPEC.json`、`方案说明.md`、`静态稿/` 已永久删除。视觉规范、静态稿与实现契约待重建；重建前不要引用旧路径，也不要用旧数值判断当前页面。

优先级规则：

1. **功能、协议、架构冲突 → 以 `AI_SPEC.json` 为准。** 暂停实现，先说明冲突点。
2. **页面行为与用户可见文案冲突 → 以 `UI设计说明.md` v3.0.0 为准。** 页面有什么功能、点击后发生什么、状态怎么变、跳到哪里、看到什么文案，都由它定义。
3. **视觉值冲突 → 暂缓。** 原 `UI_SPEC.json` 已删除，视觉规范待重建；重建前不要用旧数值覆盖页面逻辑，也不要在页面逻辑文档里硬编码新的颜色、字号、间距。
4. **实现契约冲突 → 以 `UI实现规格.md` / `AI_SPEC.json` 为准。** `UI实现规格.md` 对应旧 UI v2，待按 v3 重写；冲突时先说明，不静默沿用旧契约。
5. **有日期、有原因的设计变更优先于旧规格。** 当前有效结构是 3 Tab / 6 页面；2026-11-11 的页面逻辑重写见 `PROJECT_CHAIN.md`。
6. **人读文档与 JSON 不一致 → 按问题类型判断**：页面行为与文案看 `UI设计说明.md`；功能与协议看 `AI_SPEC.json`。
7. **静态稿重建前，不存在「静态稿与文档不一致」的问题。** 重建后，静态稿只覆盖 UI；其中的示例数据、坐标、点位名称不是接口数据。

第 3 条不是让 `PROJECT_CHAIN.md` 随意覆盖规格。一次变更要同时满足：有日期、有原因、有影响说明、并且已经写进变更记录或明确标注规格待同步。否则按旧规格做，并把疑问提出来。

完整冲突处理流程见 `references/doc-precedence.md`。

## 3. 工作协议

- **先读后写。** 改一个页面前，先读目标文件、同目录的相邻页面、以及它引用的规格片段。项目里已经有一套写法（命名、结构、class、SVG 组织），跟随它比自己另起一套更重要。
- **改动前说清范围。** 用一句话说明要改哪些文件、依据哪条规格、有没有会影响其他页面的连带修改。
- **不静默扩大范围。** 用户要改按钮颜色，不要顺手重排整个页面；发现了别的问题，记下来并在回复里提，不要混进本次改动。
- **页面改动同步文档。** 改一个页面或状态，必须同步 `UI设计说明.md` 对应页面与 §5 状态清单；静态稿重建后，再同步 `screens/`、`index.html`、`静态稿/README.md`。视觉值写视觉规范，实现契约写 `UI实现规格.md`。
- **文案不发明。** 按钮、错误标题、提示语、空状态文案取自 `UI设计说明.md` 各页面「文案」段。确实需要新文案时，先写进该段，再进入视觉稿或实现；不要在代码里临时造词。
- **数字格式统一。** 配速 `m'ss"/km`；距离展示 2 位小数、输入 1 位；时长 `mm:ss`；数字用等宽 `tabular-nums`。
- **颜色与尺寸不硬编码。** 视觉规范重建前，不要凭空引入新令牌；需要新视觉值时，先写进视觉规范并说明原因。静态稿重建后用令牌，不写裸值。
- **不引入依赖。** 新 npm 包、外部字体、CDN、图标库、统计脚本都需要先确认；这个项目的约束是「无外部资源、离线可用、无追踪」。

具体规则：

- 静态稿 → `references/frontend-standards.md` 的「静态稿」
- 未来 Vue3 → 同文件的「Vue3」
- 交付前 → `references/acceptance.md`

## 4. 思维链协议（核心）

`PROJECT_CHAIN.md` 是项目的长期记忆。这里的「思维链」指**项目层面的决策链**，不是把模型的内部推理过程写下来。它要能回答：「三个月后，一个没参与过这些对话的人，为什么看到的是现在这个界面？」

### 4.1 什么时候写

写：

- 做了一个**有取舍的决定**（选 A 不选 B，或明确不做什么）
- 完成了一个**里程碑/可交付阶段**
- **改变方向**、推翻旧决定、或发现旧决定不成立
- 发现会影响后续实现的**硬事实**（接口缺字段、平台限制、规格自相矛盾）
- 用户明确确认了一个待确认项

不写：

- 普通文件编辑、修错别字、调一个像素
- 跑一次构建、修一个语法错误
- 用户只是问问题、没有产生决定
- 可以随时从代码或规格里读出来的东西

判断标准：**这次有没有产生「以后的人会想知道为什么」的东西？** 有就写；没有就不写。流水账会让下个会话读不到重点，比不写更糟。

### 4.2 条目模板

在 `## 记录` 下面**顶部插入**（最新在上），严格用这个结构：

```markdown
### YYYY-MM-DD · 一句话标题

**背景**：为什么现在要做这个决定？约束是什么？
**决定**：具体选了什么，不选什么。
**原因**：为什么这样选；如果有替代方案，为什么没选。
**影响**：哪些文件/规格/页面因此改变；有什么代价。
**下一步**：谁来做什么；如果暂无，写「无」。
```

五段是最小充分集：只有结论会让人重复踩坑，只有背景会让人找不到决定。每条尽量控制在 8 行以内；细节多就链接到规格文件，不要复制大段内容。

### 4.3 当前状态

每次追加记录时，同步更新文件顶部的「当前状态」：

- **阶段**：一句话，例如「静态稿完成，M0 未开始」
- **已完成**：只列可交付物，不列过程
- **正在进行**：现在手上真正在做的事
- **下一步**：按优先级列 1–3 项
- **阻塞 / 待确认**：会影响实现的，带编号（GAP/Q）
- **最后更新**：日期

如果只是状态变化、没有产生决策，只更新「当前状态」，不要硬加一条记录。

### 4.4 历史规则

- **不重写历史。** 旧条目即使被推翻也保留；用新条目写「更正：……」并说明推翻了哪条。
- **一条记录只讲一个决定。** 不要在一次提交里塞三个不相关的决定。
- **链接而不是复制。** 写 `UI设计说明.md` 的章节号、文件路径、页面名，不要把整段规格抄进来。
- **压缩而不删除。** 文件超过 200 行或 30 条记录时，把最老的若干条合并成「阶段摘要」，保留每个决定的「决定 + 原因」；不要直接删掉。
- **日期用绝对日期**（`2026-11-05`），不要写「今天」「上周」。

### 4.5 结束前自检

每次任务结束前问自己：

1. 这次有没有产生决策或里程碑？有 → 写；没有 → 不写。
2. 如果有写：新条目是否包含背景/决定/原因/影响/下一步？「当前状态」是否同步？
3. 有没有为了让任务通过而偏离规格？有 → 必须在回复里说明，并按 §2 记录变更。
4. 有没有把临时调试信息、个人猜测写进思维链？有 → 删掉或标为「假设」。

然后在最终回复里明确报告：

- 写了：`思维链：已追加「<标题>」`
- 没写：`思维链：本次无需更新（<一句话原因>）`

这个报告不是形式主义。它让用户能确认「项目记忆有没有跟上」，也让你自己意识到这次改动是不是只改了表面。

## 5. 交付前验证

- 页面逻辑文档改动：在仓库根目录运行
  ```bash
  python -I .claude/skills/campus-run-frontend/scripts/check_docs.py
  ```
  它会检查 6 个页面章节、每页必需字段；`静态稿/` 存在时再检查文档 / README / screens 双向覆盖。检查失败就不要说「完成」。
- 静态稿改动：静态稿重建后，再运行
  ```bash
  python -I .claude/skills/campus-run-frontend/scripts/check_static.py
  ```
  它会检查页面是否存在、索引是否覆盖、链接是否断、是否误引入脚本或外部资源。
- 2026-11-11 起 `静态稿/` 已删除；重建前只跑 `check_docs.py`，并在回复里说明「静态稿未重建，未跑 check_static」。
- Vue 改动：至少跑类型检查与构建（以 M0 定下的命令为准）；没有工程时不要假装跑过。
- 按 `references/acceptance.md` 过一遍对应清单。
- 在回复里写清：跑了什么、结果如何、没跑什么、为什么。

## 6. 回复结构

普通任务按这个顺序，短任务可以合并段落，但不要漏掉第 1、4 项：

1. **定位**：项目一句话 / 当前阶段 / 本次依据
2. **改动**：改了哪些文件，关键决定是什么
3. **验证**：跑了什么检查，结果如何
4. **思维链**：已追加哪条，或为什么没更新
5. **待确认**（如有）：需要用户拍板的事

不要用大段总结复述规格。用户要的是「你做了什么、依据是什么、下一步是什么」。
