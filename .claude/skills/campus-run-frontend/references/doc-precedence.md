# 文档优先级与冲突处理

这个项目的规格不是静止的。`UI_SPEC.json` 已升到 2.0.0，静态稿在 2026-11-05 又改过一次信息架构。所以「哪份文档说了算」必须按问题类型和日期判断，不能背一条固定优先级就完事。

## 1. 按问题类型找权威源

| 问题 | 权威源 | 备注 |
| --- | --- | --- |
| 这个功能能不能做？协议怎么走？ | `AI_SPEC.json` | 功能、协议、桥、错误码、里程碑的最高事实源 |
| 桥方法签名、线程、安全存储、ABI | `AI_SPEC.json` | 不要用前端文档反推 |
| 页面有什么功能、点击后发生什么、状态怎么变、跳到哪里 | `UI设计说明.md` | 页面行为事实源；当前以静态稿 2026-11-06 状态为准 |
| 页面尺寸、令牌、文案原文是什么？ | `UI_SPEC.json` | UI 规范值；`normative: true`，但不定义页面行为 |
| 接口调用、桥方法、错误码、脱敏、功能标注、GAP / 假设 | `UI实现规格.md` | 实现契约；静态稿阶段不维护 |
| 实际做出来的视觉与跳转 | `静态稿/` | 只代表 UI 层，不代表接口行为 |
| 哪些地方有意偏离了规格 | `静态稿/README.md` 的「设计变更」 | 每条都有日期和原因 |
| 为什么变成现在这样、下一步是什么 | `PROJECT_CHAIN.md` | 决策链；不是功能规格 |
| 项目身份、架构、边界 | `PROJECT.md` | 稳定信息；方向变了才改 |

## 2. 冲突场景

### 2.1 `UI_SPEC.json` vs `AI_SPEC.json`

以 `AI_SPEC.json` 为准。`UI_SPEC.json` 的 `readingContract` 自己写了：「与 AI_SPEC.json 冲突时，以 AI_SPEC.json 为准；若需暂停实现等待确认。」

做法：

1. 停下来，指出冲突的具体字段（例如 `screens[].states` vs `stateMachines`）。
2. 不要自行选一个看起来合理的版本继续写。
3. 在回复里给出两个选项和影响，让用户拍板。
4. 拍板后写思维链条目，并更新相应规格。

### 2.2 静态稿 vs `UI_SPEC.json`

先查 `静态稿/README.md` 的「设计变更」：

- **变更里写了**：这是有意偏离，以变更记录为准。例如 2026-11-05 的首页合并、3 Tab、移除登录页 SafetyBanner。
- **变更里没写**：静态稿是错的，或者规格过期了。不要默认「静态稿就是对的」；先判断是哪一种，再修对应的一边。
- 不确定时，看 `PROJECT_CHAIN.md` 有没有对应决策；没有就问用户。

### 2.3 `PROJECT_CHAIN.md` vs 规格

思维链记录的是「决定」，不是「规范文本」。它可以在规格还没同步时代表当前方向，但有边界：

- **可以覆盖**：已经明确记录、有日期、有原因的设计变更。例如「首页合并为跑步页」。
- **不能覆盖**：`AI_SPEC.json` 里的功能/协议事实，除非用户明确同意改功能，并且 `AI_SPEC.json` 已更新或标注待改。
- **不能覆盖**：安全约束、平台约束、不变量（无后端、Python 3.12、ABI、敏感值不入前端）。

如果思维链和规格不一致，正确做法不是「以新的为准」就完事，而是：按思维链做当前任务 + 在回复里标注「规格待同步」+ 提议同步规格。长期让两者不一致，下个会话一定会踩坑。

### 2.4 页面逻辑 vs `UI_SPEC.json`

按问题类型判断，不再「一律以 JSON 为准」：

- **页面行为**（功能、点击效果、状态、跳转、用户可见流程）→ `UI设计说明.md`。
- **视觉值**（颜色、字号、间距、组件尺寸）与**文案原文** → `UI_SPEC.json`。
- 两者冲突时：先判断问题属于行为还是数值。行为冲突不要自行选一边，先问；数值冲突改 `UI设计说明.md` 的引用，不要把数值抄进去。
- `UI设计说明.md` 里的页面状态文案应与 `UI_SPEC.json` 的 `screens[].copy` / `copyDeck` 一致；不一致时以 JSON 的文案原文为准，并修正页面逻辑文档的引用，或先把新文案写进 JSON。
- `UI_SPEC.json` 2.0.0 已最小同步为 3 Tab；`console` / `runSetup` 标记 superseded，`runHome` 为当前首页。页面行为以 `UI设计说明.md` 为准；完整迁移仍待后续。

### 2.5 静态稿 vs 真实接口

静态稿里的数据是示例，不是接口契约。点位名称、坐标、消耗 kcal、轨迹点数量都可能是编的。接口字段以 `AI_SPEC.json` 的 `dataModels` / `apiEndpoints` 和协议代码为准。

## 3. 偏离规格的完整流程

任何「不按现有规格做」的改动，都要走完这四步，缺一不可：

1. **确认**：向用户说明要偏离哪条规格、为什么、替代方案是什么，得到明确同意。
2. **记录变更**：在 `可视化页面/静态稿/README.md` 的「设计变更」追加一条，格式：
   ```markdown
   - YYYY-MM-DD：<改了什么>。原因：<为什么>。影响：<哪些规格/页面失效>。
   ```
3. **写思维链**：在 `PROJECT_CHAIN.md` 顶部追加条目，写清背景/决定/原因/影响/下一步。
4. **同步规格**：
   - UI 相关：更新 `UI_SPEC.json` 的 `designChanges`，必要时升版本并在 `maintenance.versionHistory` 记一笔。
   - 功能/协议相关：更新 `AI_SPEC.json` 的对应字段；如果暂时不能改，明确标注「待同步」，不要假装已经一致。

只做第 1 步（口头同意）不算记录；只改静态稿不写变更记录，下个会话会把它当 bug 修回去。

## 4. 什么时候必须停下来问

以下情况不要自行决定，先问：

- `AI_SPEC.json` 与 `UI_SPEC.json` 冲突，且影响页面行为。
- `UI设计说明.md` 与 `静态稿/` 对不上，且无法判断是哪边漏改。
- 需要改 `协议/`、Kotlin、Chaquopy 或桥方法签名。
- 需要新增接口字段、改数据模型、改错误码。
- 需要新增 npm 依赖、外部资源、网络请求域名。
- 涉及 token、密码、盐、验证码、设备标识的展示或存储。
- 规格里标为 `blocking` 的 GAP（当前是 GAP-02 `runAreaId`）。
- 用户的要求会让「有效性」「成功/失败」「已取消/未知」的含义发生变化。

## 5. 更新规格的规则

- **页面行为**：先改 `UI设计说明.md`，再改 `静态稿/`，同步 `index.html`、`静态稿/README.md` 与页面逻辑文档的状态表（四处同步）。
- **视觉值与文案原文**：先改 `UI_SPEC.json`，再同步 `spec.css` 与 `UI设计说明.md` 的引用。
- **实现契约**：先改 `UI实现规格.md` 与 `AI_SPEC.json`，再改桥接代码；静态稿阶段不主动改。
- **新增 / 删除状态**：四处同步，并跑 `check_static.py` + `check_docs.py`。
- 改 JSON 要升版本号，并在 `maintenance.versionHistory` 写日期和变更摘要。
- 不要删除历史条目；用 `designChanges` / `status: superseded` / 新版本记录表达「旧的决定被替代」。
- GAP 关闭后标 `status: closed` 和版本号，不删除历史。
- 文案的唯一来源是 `screens[].copy` / `copyDeck`；新增文案要进规范，不要只活在页面里。

## 6. 一个判断口诀

> 功能问 AI_SPEC，行为问 UI设计说明，数值文案问 UI_SPEC，落地看静态稿，接口看 UI实现规格，原因看思维链；日期更晚的明确决定优先，但必须留下痕迹。

如果读完这条还是不确定，就停下来问。猜错的成本比多问一句高。
