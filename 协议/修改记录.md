## 2026-11-17 · EdgeOne 坏节点：地址级回退 + 跑步链路重试

**背景**

- 2026-11-17 12:16:40 的一次真实提交在 `申请 OBS 上传凭证` 失败：`<urlopen error [WinError 10054] 远程主机强迫关闭了一个现有的连接。>`，耗时约 19 s；轨迹已落盘 outbox，服务端未写入成绩。
- 现场复现：`run.gxapp.iydsj.com` CNAME 到 EdgeOne，DNS 轮换多个边缘 IP；`116.196.150.245` 可以完成 TCP 连接，但 TLS 握手在 **18.69 s / 19.66 s** 时以 `SSLEOFError` 断开；`119.188.175.46`、`221.204.163.76` 的 TLS 只需 0.01–0.06 s。
- Python `socket.create_connection` 只在 **TCP** 阶段失败时换下一个地址；TCP 连上后 TLS 失败不会回退。`core/client.py` 又是单次 20 s、零重试，正好卡在 EdgeOne 的故障/限流时间带内。

**修改**

1. 新增 `7.3.92/core/net.py`
   - `NodeSelector`：按主机缓存最近一次 TCP+TLS 成功的边缘 IP，进程内 TTL 300 s；失效后重新解析。
   - `EdgeHTTPSConnection`：把「TCP + TLS」放进同一个逐地址循环，单地址预算 4 s，任何失败立即换下一个；成功后把 IP 写回缓存。代理隧道（`_tunnel_host`）直接回退原生实现。
   - `build_https_opener()`：保留代理、重定向与错误处理的 urllib opener。
   - 环境变量 `CAMPUSRUN_NODE_PIN=0` 可临时关闭该行为。
2. `7.3.92/core/client.py`
   - `execute_request` 拆成「重试外壳 + `_execute_once`」；默认超时 20 s → 35 s。
   - 新增 `retries` / `log` 参数，只重试网络层异常（`OSError` / `URLError` 中的 OSError）；`HTTPError` 与解析错误不重试。
   - 改用带地址回退的 `self.opener`。
3. `7.3.92/login/client.py`：使用同一个 opener（登录预检也享受地址回退）。
4. `7.3.92/running/client.py`
   - `request_obs_url`（Put/Get 预签名）最多 3 次尝试、1.5 s / 3.0 s 退避；每次重试重新生成 nonce / timeStamp / headerSign。
   - `get_rundetail_config` 允许 1 次重试。
   - `submit_record` 保持不自动重试（可能已被服务端写入，避免重复成绩）。
   - OBS 凭证失败文案补充「上游边缘节点连接异常；轨迹已保存，可稍后重试」。
5. 新增 `test_net_selector.py`（6 项）与 `test_client_retry.py`（10 项）。

**原因**

- 只加重试不够：Windows DNS 有缓存，1.5 s / 3 s 的退避很可能拿回同样的 IP 顺序；而 TLS 阶段失败时标准库不会换地址，必须由客户端自己逐地址完成 TCP+TLS。
- OBS 预签名只换取 URL、不写服务端状态，是幂等请求，可以安全重试；成绩结算不是幂等请求，保持人工/outbox 重试。

**影响**

- 正常请求仍一次往返；只有坏节点会消耗 4 s 单地址预算。
- 首次请求最坏多等 (N−1)×4 s；成功后进程内缓存，后续请求回到 0.2 s 级。
- 未改签名算法、报文结构、轨迹生成、结算时序与 OBS 对象 Key。

**验证**

- `python -X utf8 -m unittest discover -p "test_*.py"`：134 项全过（原 118 + 新增 16）。
- 真实只读（无凭据、未提交成绩）：把已知坏 IP `116.196.150.245` 注入 DNS 首位，首次请求 **4.20 s** 跳过坏节点并返回 `401`（已到达业务层）；随后两次 **0.19 s / 0.90 s**，候选顺序变为好 IP 在前，缓存命中。
- `LoginClient` / `SportClient792` 构造通过；`python -m py_compile` 通过。
- 按要求未执行任何真实登录、取点或成绩提交。

**待确认**

- 下次真实提交观察日志中的重试次数与节点切换；若仍出现 20 s 级延迟，需要抓包区分 EdgeOne 队列与源站排队。

## 2026-11-17 · 登录链路放宽超时并给只读预检重试，超时不再甩英文堆栈

**背景**

- 2026-11-17 10:40:58 的一次运行在 `checkGeeUse` 卡死 27.8 s 后失败：`TimeoutError: The read operation timed out`，异常从 `login/client.py` 直接穿透到 `runner.py`，界面只看到英文堆栈。
- 堆栈停在 `ssl.read → _read_status`，说明 DNS、TCP、TLS 均已完成、请求已发出，是服务端/CDN 没有回响应；不是连不上。
- 现场对同一接口（同设备 ID、同账号）连测 10 次：前 5 次 0.13–0.17 s；第 6 次 `RemoteDisconnected` 34.3 s；第 7–9 次均在 **20.15 s** 才返回；第 10 次 `URLError` 27.1 s。
- 历史日志同样出现过：11-16 10:16 / 10:19 的 `checkGeeUse` 与随后的 `geevalidate` 都是整 20 s，11-16 10:41 为 17 s。`run.gxapp.iydsj.com` 的 CNAME 指向 `.eo.dnse2.com`（腾讯 EdgeOne），属于边缘节点在高频请求后的限流/排队。
- 旧实现单次 `timeout=20`、零重试，正好卡在限流区间内；`/login` 超时后也无法区分「密码错」与「结果未知」。

**修改**

1. `7.3.92/login/client.py`
   - `execute_request` 拆成「重试外壳 + `_execute_once`」：`timeout` 默认 35 s，新增 `retries` 与 `log` 参数；每次重试重新生成 nonce / timeStamp / headerSign。
   - 重试只针对网络层异常（`TimeoutError`、`URLError`、`ConnectionError`、`RemoteDisconnected`、`ssl`/`gaierror`），`HTTPError` 等已拿到状态码的错误立即返回。
   - `checkGeeUse` 重试 2 次（共 3 次，退避 1.5 s / 3.0 s）；`geevalidate` 重试 1 次（极验凭据一次性，不宜多刷）；`/login` **不自动重试**。
   - 重试耗尽抛 `LoginNetworkError`；`login()` 把它转成中文 `LoginResult(code=-1)`：预检超时提示「上游限流，5–10 分钟后重试」，`/login` 超时提示「结果未知，先到官方 App 确认，不要立即重试」。
2. `电脑一键启动/runner.py`
   - 新增 `_friendly_exception()`：把 `TimeoutError` / `URLError` / `ConnectionError` / `OSError` 转成中文失败文案，异常堆栈仍写入日志。
   - 新增 60 s 运行冷却（`MIN_RUN_INTERVAL_SEC`，以 `logs/` 最新 mtime 为准），冷却期内直接返回「请求过于频繁」；`CAMPUSRUN_SKIP_COOLDOWN=1` 可跳过（供脚本/测试）。

**原因**

- 上游限流是周期性、可恢复的，只读预检重试的收益远大于成本；`/login` 超时若自动重试，会把「结果未知」变成额外的密码错误次数（账号已有 1 小时锁定机制），因此必须人工确认。
- 超时从 20 s 提高到 35 s，覆盖实测 20 s 级别延迟并留出连接退化余量；代价只在下游真故障时体现。

**影响**

- 正常请求仍是一次往返；`checkGeeUse` 最坏耗时约 3 × 35 s + 4.5 s，`geevalidate` 约 2 × 35 s + 1.5 s，且只在网络异常时触发。
- 失败文案由英文异常名变为中文提示；`login()` 仍返回 `LoginResult`，`cli.py` 与 `sport_client.py` 无需改动。
- 上传字段、签名算法、极验参数、跑步链路均未改动。

**验证**

- `python -m py_compile`：`login/client.py`、`runner.py` 通过。
- 离线单测（monkeypatch `_execute_once`）：`checkGeeUse` 前两次超时、第三次成功 → 3 次尝试、4.5 s 后返回；`submit_login` 超时只尝试 1 次；`login()` 返回中文 `LoginResult`；`HTTPError 500` 判定为不可重试；`runner.run` 在冷却期直接返回、不建日志。
- 真实只读请求：同设备 ID 调用 `checkGeeUse`，0.21 s 返回 `{'error': 10000, 'message': '成功', 'data': False}`。
- 未执行真实登录与提交（账号存在单设备保护与密码错误锁定风险）。

**待确认**

- 若 35 s 仍频繁超时，下一步应抓包确认是 EdgeOne 连接层限流还是源站排队；必要时把客户端请求节奏（运行间隔）继续拉长。

## 2026-11-16 · 手动折返路线采样：补偿段沿原路继续，不再直线跳回起点

**背景**

- 《手动路线折返展开方案》要求手画路线短于目标时沿原路反向折返；桌面端已把「长度 = 目标」的展开折线交给协议。
- `sample_route()` 的 `_sample_track()` 按 `route[edge % len(route)]` 把折线当闭环；整秒采样切掉拐角后补偿循环需要多走 1–3 m，对开放折线会从终点**直线跳回起点**，产生手画折线之外的坐标，且固定点迭代在折返几何上来回震荡、弦长收敛不到目标（`check_track` 会报 `track length ... differs`）。
- 离线 dry-run 复现：rrid `1366205871` 的真实 5 点 + 2637.6 m 手画路线、3050/3056 m 目标，旧逻辑弦长偏 3–8 m。

**修改**

- `7.3.92/running/consistency.py`
  - 新增 `FOLDBACK_TOLERANCE_M=0.5`、`FOLDBACK_MARGIN_M=20.0`。
  - 新增 `_is_foldback_route()`：折线长度≈目标且首尾不重合时判定为“手动折返路线”。
  - 新增 `_foldback_point()` / `_extend_for_foldback()`：沿展开折线里已有的同一直线段继续 61 m（`FOLDBACK_MARGIN_M=60` + 1 m 余量），作为补偿采样点（点在原折线上，不新增几何）。
  - 新增 `_solve_foldback_traverse()`：从目标距离向外扫描，取第一个弦长命中（±0.02 m）的补偿距离，遇到变号再局部二分；替代会震荡的固定点迭代。
  - `sample_route()`：只对手动折返路线走上述分支；其它路线（OSM 闭环、合成路线）仍用原固定点迭代。
- `test_run_consistency.py`
  - 新增「长度=目标开放折线折返回不跳回起点」和「折返扩展只对开放等长路线生效」两项测试。

**未修改**

- 上传字段、`check_track`、时间轴整秒规则、指标、签名、OBS、结算、回查全部不变。
- OSM 闭环路线与自由跑合成路线不进入折返分支，行为不变。

**影响**

- 手动路线补偿多走的几米沿手画折线继续，轨迹点全部落在手画线上；弦长精确等于目标。
- 折线长度与目标相差 >0.5 m、或首尾重合的路线完全走原逻辑。

**验证**

- `python -m unittest discover -p "test_*.py"`：118 项全过（原 116 + 新增 2）。
- 离线 dry-run（真实 5 点 + 清理后的 2636.42 m 路线）：
  - 3050 m / 1321 s：441 点，弦长 3050.000，最大偏离手画线 0.0041 m，配速 6.83–8.07 min/km，0 个 0 秒差，5 点顺序 1–5，建筑/边界通过；旧轨迹 16 点偏离、最大 37.3 m，新轨迹 0 点偏离。
  - 3056 m / 1222 s：408 点，弦长 3056.000，配速 6.19–7.20 min/km，其余同上。
- 未执行真实提交。

**下一步**

- 用真实账号做一次受控提交，确认官方 App 轨迹与手画路线重合、无斜线，OBS 点数/长度与本地一致。

## 2026-11-16 · 取点锚点：官方 5 点接口改用指定 GCJ 坐标

**背景**

- 官方 5 点接口 `/api/v560/get/1/distance/{minDistance}` 本来就接收 `latitude/longitude`；官方 App 传当前 GPS，脚本一直传围栏多边形第一个顶点，导致每次取点位置固定、返回的点集中在同一片区域。
- 《锚点就近取点方案》（2026-11-16 确认稿）要求：客户端在地图上画 1–5 个锚点，每次运行随机选 1 个作为取点位置；官方返回哪 5 点仍由服务端决定。
- 路线库未命中时需要显式选择「手动画线 / OSM 自动规划 / 取消」，且**不重新取点**（官方限 5 分钟 3 次）。

**修改**

1. `7.3.92/policy/client.py`
   - 新增 `normalise_anchor_gcj()`（支持 `(lat, lon)` 与 `glat/glon` 字典，限中国范围）、`point_in_polygon()`、`fence_gcj_polygon()`。
   - `get_checkpoints_for_run(..., anchor_gcj=None)`：有锚点用锚点，并在发请求前用官方围栏 GCJ 多边形校验；锚点越界直接失败，不发取点请求。无锚点仍回退围栏第一个顶点（旧行为）。
   - `get_run_checkpoints(..., anchor_gcj=None)`：锚点覆盖 `latitude/longitude`；新增 `last_checkpoint_anchor` 记录本次实际使用的坐标与来源。
2. `7.3.92/running/models.py`
   - 新增 `RouteDecision`（`manual` / `osm` / `cancel`），兼容旧的 `(polyline, ordered)` 与 `None` 返回值。
3. `7.3.92/running/client.py`
   - `execute_full_run(..., anchor_gcj, anchor_id, anchor_name)`：校验并透传锚点；有锚点时强制取当天点位；`RouteContext` 增加三个锚点字段；日志打印 `取点锚点`。
   - provider 返回 `RouteDecision.osm()` 时复用本次点位改走 OSM（不重新取点）；`cancel()` 返回 `manual_route_cancelled`。
4. `7.3.92/sport_client.py`
   - `execute_run()` 透传 `anchor_gcj / anchor_id / anchor_name`。
5. 测试
   - `test_checkpoints.py`：锚点覆盖围栏顶点、锚点越界/非法不发请求、`execute_full_run` 透传锚点、`RouteDecision.osm()` 只取一次点、`RouteDecision.cancel()` 不上传。
   - `test_run_consistency.py`：`RouteDecision.osm()` 复用当次点位并走 OSM。

**未修改**

- 提交字段、签名、轨迹采样、OBS、结算、回查均未改动；锚点只影响取点请求的两个坐标值和本地日志/路线库历史。

**影响**

- 未配置锚点时行为不变（围栏第一个顶点）；配置锚点后取点位置由用户决定。
- 锚点不在官方围栏内时整次运行在取点阶段失败，文案为「锚点不在官方围栏内，请重新绘制」。
- provider 现在可以显式取消（`manual_route_cancelled`）或改走 OSM；`None` 仍按「未返回路线」失败，不静默回退。

**验证**

- `python -m unittest discover -p "test_*.py"`：116 项全过（原 108 项 + 新增 8 项）。
- 离线单测覆盖请求体坐标、越界拦截、`last_checkpoint_anchor`、一次取点与两种决策；未执行真实登录/取点/提交。

**下一步**

## 2026-11-16 · 学校规则接口失败可见并可重试，避免一次网络抖动废掉整次跑步

## 2026-11-15 · 轨迹时间轴改为整秒，修复配速图剧烈尖刺

## 2026-11-07 · 修正 speed 单位与成绩有效性判定

**背景**

- 2026-11-06 使用账号 `账号B` 提交 `3000m / 1060s`，返回 rrid `1357787548`。
- 官方 App 的配速显示约为 `2'30"–2'50"/km`，而按距离/时长计算应为 `5'53"/km`。
- 回查 `get_one_record` 得到：`totalTime=1060`、`totalDis=3000`、`speed=2.83`、`speedTop=4.0`、`speedBottom=12.0`；`reasonList` 中「配速控制在4′00″-12′00″」为 `complete:false`；`statusInfo` 为「检测到跑步数据异常，本次成绩无效」；`status=1`、`unCompleteReason=0`。
- 官方 App 反编译确认：
  - `UploadFormatEntity.setSpeed(double d)` 执行 `(long)(round(d, 2) * 1000)`，即上报字段是 **分钟/公里 × 1000**。
  - `Utils.OooOOo(double)` 把该值按 **分钟/公里** 显示（整数分钟 + 小数部分 ×60 秒）。
  - `RunHistoryDetailPImpl` / `RunHistoryAdapter` 以 `status == 0` 为达标，`status == 1` 为未达标。

**修改**

1. `协议/7.3.92/running/builder.py`
   - `speed_val` 由 `round(distance / time * 1000)`（米/秒 ×1000）改为 `int(round((time / 60) / (distance / 1000), 2) * 1000)`（分钟/公里 ×1000）。
   - `3000m / 1060s`：旧值 `2830`（官方显示 `2'50"`）→ 新值 `5890`（官方显示 `5'53"`）。
2. `协议/7.3.92/history/models.py`
   - `RunRecordDetail.from_api_data()`：达标判定由 `status == 1` 改为 `status == 0`，并检查 `complete` 与 `reasonList` 中所有条件均通过。
   - `history_record_status()`：状态语义改为 `0=达标`、`1=未达标`、`2=不达标，存在异常`。
   - 新增 `format_pace()`（服务端返回的 `speed`，分钟/公里）与 `format_scaled_speed()`（上报字段，分钟/公里 ×1000）。
3. `协议/7.3.92/running/client.py`
   - 轨迹日志里的「配速」不再打印原始 `5890`，改为 `5'53"`。
4. `协议/7.3.92/history/cli.py`
   - 单条回查的配速改用 `format_pace()`；列表状态统一走 `history_record_status()`。
5. `协议/7.3.40/credit_run.py`
   - 两处 `speed_val` 同步改为「分钟/公里 ×1000」。
6. 测试
   - `协议/7.3.92/test_history_cli.py`：状态语义、达标判定、配速格式化。
   - `协议/7.3.92/test_run_consistency.py`：新增上报 `speed` 单位回归（`2150m / 760s → 5890`）。

**原因**

- `speed` 单位错位，服务端把 `5'53"/km` 解读为 `2'50"/km`；该值低于学校配速下限 `4'00"`，因此配速项失败、成绩被判无效。
- CLI 的达标判定把 `status == 1` 当作达标，与官方 App 的 `status == 0` 相反，导致误报「达标」。

**影响**

- 2026-11-06 的 rrid `1357787548` 仍然无效，改代码不能追溯修复；需要重新提交一次。
- `--history` / `--rrid` 的显示会变化：旧记录显示 `2'50"`，新记录显示 `5'53"`；状态文案按官方语义显示。
