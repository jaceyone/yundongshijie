# 锚点就近取点方案

> **状态**：已实现（桌面端）· 2026-11-16。协议侧锚点参数、`RouteDecision`、桌面端锚点池/编辑器/未命中三选一均已落地；**尚未执行任何真实登录、取点或提交**。
> **定位**：把「官方 5 点从哪来」从固定围栏顶点改为用户在地图上绘制的锚点池；每次运行随机选 1 个锚点，作为官方取点接口的 `latitude/longitude`。
> **关系**：建立在 `手动路线与路线库方案.md` 与 `OSM自动轨迹生成与上传方案.md` 之上；OSM 自动路线仍是回退路线源。
> **前提**：官方取点接口会根据传入坐标就近返回 5 个点位。该前提由用户确认；落地前仍需一次**只读取点实验**验证（见 §11）。
> **已确认**：锚点池允许 **1–5 个**；随机不避重（允许连续同一锚点）；路线起点**不强制**等于锚点；锚点写入路线库历史与运行日志。
> **结论**：客户端实现简单（只是换两个请求字段）；真正的未知量是服务端是否按锚点就近选点，以及锚点变化能否带来不同的 5 点集合。

---

## 0. 一页结论

- 用户在地图上画 **1–5 个锚点**（推荐 5 个，A1–An），保存在本地 `anchor_points.json`。
- 每次运行随机选 **1 个**锚点，把它作为 `/api/v560/get/1/distance/{minDistance}` 的 `latitude/longitude` 发给官方；允许连续两次选到同一个锚点。
- 官方返回 5 个点位；**客户端不参与选点**，只参与选锚点。
- 返回的 5 点先按现有 `points_key` 查路线库：
  - 命中 → 复用已有手动路线；
  - 未命中 → 让用户选「手动画线 / OSM 自动规划 / 取消」。
- 不改提交字段、签名、轨迹生成、OBS、结算；只改取点请求里的锚点坐标，并新增路线决策分支。
- **方案是否达到目的，取决于服务端行为**：若官方忽略锚点，则 5 点仍固定，锚点池只保留记录与可追溯价值。

## 1. 背景与目标

### 1.1 现状

当前取点链路（`协议/7.3.92/running/client.py` → `policy/client.py`）：

1. `execute_full_run()` 先取学校规则，再取围栏 `geoFences`；
2. 计分跑调用 `policy.get_checkpoints_for_run(fence, uuid, rule)`；
3. `get_checkpoints_for_run()` 使用 **围栏多边形的第一个顶点**作为锚点：

```python
latitude, longitude = fence.polygon_points[0].gcj_coordinates()
```

4. 请求官方 `/api/v560/get/1/distance/{rule.min_distance}`，返回 `pointsResModels`（5 个点）；
5. 手动路线模式用这 5 点匹配路线库；命中则复用，未命中直接报 `manual_route_missing`，**不会自动回退 OSM**。

这个第一个顶点是围栏边界上的固定点，不是用户的位置，也不是跑步起点。用户观察到的“每次都是同一组点、集中在同一片区域”，与这个固定锚点一致。

### 1.2 目标

1. 取点位置由用户决定：在地图上绘制 **1–5 个锚点**（推荐 5 个），形成锚点池。
2. 每次运行从锚点池随机选 1 个，作为官方取点接口的“当前位置”；允许连续同一锚点。
3. 官方按这个位置就近返回 5 个点位；脚本使用官方返回的 5 点，不自行编造。
4. 当返回的 5 点是新集合、路线库没有对应路线时，让用户明确选择：
   - 手动画线（现有编辑器）；
   - OSM 自动规划（复用现有避建筑规划）；
   - 取消本次提交。
5. 整个过程可追溯：日志能看到本次锚点、返回的 5 点、`points_key`、路线决策。
6. 不改变官方上报字段、签名、OBS 结构、结算与回查逻辑。

### 1.3 非目标

- 不修改服务端行为，不伪造官方点位。
- 不做“刷新到拿到新点集为止”的自动循环（官方 5 分钟最多 3 次）。
- 不自动从官方点位中生成锚点池；锚点由用户绘制。
- 不改变目标距离、时长、配速、步频、轨迹生成算法。
- 首版只覆盖桌面端 `电脑一键启动`；Android Vue3 控制台尚未开始（M0），不在本次范围。
- 不做多账号、服务端同步、云端锚点共享。

## 2. 事实、假设与证据

### 2.1 官方取点接口事实（反编译）

来自 `_analysis/out_dex7/.../CommonApiManager$requestFivePoint$1.java` 与 `RunStartViewModel.java`：

| 事实 | 说明 |
| --- | --- |
| 端点 | `POST /api/v560/get/1/distance/{distance}` |
| 请求体 | `longitude`、`latitude`、`selectedUnid`、`uuid`、`runec`、`runAreaId`、`sign` |
| 锚点 | 官方 App 传**当前 GPS 的 GCJ-02 坐标**（`mValidLatLng.getgLng()/getgLat()`） |
| 距离 | 官方 `mDistance` 默认取 `RunRuleModel.minDistance`（本项目为 1000 m），与当前脚本一致 |
| 选择模式 | 顺序跑与随机跑调用同一个接口；客户端只决定“按顺序通过”还是“经过两个普通点和必经点” |
| 客户端随机 | 只随机 5 个点的**顺序**（`calculateRouteWrapper` 在距离窗口内随机选排列），不随机点位本身 |
| 限流 | 5 分钟内最多 3 次，第 4 次返回 `code=10603` |

### 2.2 现实现的差异

| 项 | 官方 | 当前脚本 |
| --- | --- | --- |
| 锚点来源 | 当前 GPS | 围栏多边形第一个顶点（固定） |
| 锚点坐标系 | GCJ-02 | GCJ-02（一致） |
| 距离参数 | `minDistance` | `rule.min_distance`（一致） |
| 请求体其它字段 | 一致 | 一致 |
| 5 点顺序 | 客户端随机排列 | 自动模式 `select_official_order`；手动模式用路线库 `order` |

**唯一需要改的协议差异就是锚点坐标来源。**

### 2.3 已观察到的点位行为

来自 `电脑一键启动/logs/points-20261113-171617.json` 与 `route_history.jsonl`：

- 同一 5 分钟窗口内连续取 3 次（3 个不同 `uuid`）：返回**完全相同**的 5 点，连顺序都相同；
- 第 4 次立即返回 `10603`；
- 跨时间会变化，典型形态是「4 个共同点 + 1 个轮换点」：

```text
集合 A：公寓1、公寓2、公寓4、路线1、路线2
集合 B：公寓1、公寓4、路线1、路线2、路线4
```

- 同一组坐标的不同次响应里，`isFixed=1` 落在不同点上（路线2 / 公寓1 / 路线1），说明这是服务端为本次运行指定的“必经点”，不是客户端能控制的。

这些证据说明：服务端在短时间内会缓存/固定一组点，但跨时间会轮换。**它们还不能证明锚点参与选点**，因为脚本从未换过锚点。

### 2.4 本方案的前提

本方案采用用户确认的前提：

> 官方取点接口会根据传入的 `latitude/longitude`，就近返回 5 个点位。

在正式实现前，用 §11 的只读实验验证。实验只调规则/围栏/取点三个读接口，不上传成绩；使用测试账号，避免顶掉主账号手机端。

## 3. 方案概述

```text
用户在地图上绘制 A1–An（1 ≤ n ≤ 5）
        │  保存
        ▼
anchor_points.json（GCJ-02，本地，gitignore）
        │
        ▼  每次运行
随机选 1 个锚点 anchor（记录 id / 坐标 / seed）
        │
        ▼
登录 → 取规则 → 取围栏
        │
        ▼
POST /api/v560/get/1/distance/{minDistance}
  latitude = anchor.glat
  longitude = anchor.glon
  selectedUnid / uuid / runec / runAreaId / sign 不变
        │
        ▼
官方返回 5 点 pointsResModels
        │
        ├─ 计算 points_key → 路线库命中
        │       → 复用已有手动路线（现有流程）
        │
        └─ 未命中
                → 弹窗：手动画线 / OSM 自动规划 / 取消
                     ├─ 手动画线：打开编辑器，保存后继续
                     ├─ OSM：用同一组 5 点走现有官方排序 + OSM 规划
                     └─ 取消：不提交，结束
```

关键点：**只取一次点**。无论用户选手动还是 OSM，都复用这一次请求返回的 5 点，不能因为路线决策再请求一次（会消耗 5 分钟 3 次的配额，而且可能返回另一组点）。

## 4. 锚点池

### 4.1 数据模型

新文件：`电脑一键启动/anchor_points.json`（加入 `.gitignore`，理由与 `route_library.json` 相同：包含真实校园坐标）。

```json
{
  "version": 1,
  "updated_at": "2026-11-16T12:00:00",
  "unid": 17601,
  "campus": "xuchang_280173698",
  "selection": "random",
  "avoid_last": false,
  "last_used_id": "a3",
  "points": [
    {"id": "a1", "name": "操场东门", "glat": 34.000000, "glon": 113.000000},
    {"id": "a2", "name": "宿舍区",   "glat": 34.000000, "glon": 113.000000},
    {"id": "a3", "name": "教学楼",   "glat": 34.000000, "glon": 113.000000},
    {"id": "a4", "name": "校门",     "glat": 34.000000, "glon": 113.000000},
    {"id": "a5", "name": "食堂",     "glat": 34.000000, "glon": 113.000000}
  ]
}
```

> 上表坐标是占位值，不是真实校园坐标；实际坐标由用户在地图上绘制后写入。
> 保存时尚未登录，实现会从最近一次取点报告 `logs/points-*.json` 推断 `unid`；推断不到时留空，不影响使用。

字段说明：

| 字段 | 说明 |
| --- | --- |
| `version` | 文件格式版本，首版为 1 |
| `unid` / `campus` | 命名空间；锚点只对同一学校/校园有效 |
| `selection` | `random`（随机）或 `rotate`（轮换，后续可选） |
| `avoid_last` | 首版固定 `false`：允许连续选到同一个锚点；保留字段便于以后开启“不连续重复” |
| `last_used_id` | 上次使用的锚点，**仅记录与界面提示**，不参与选择 |
| `points` | 允许 1–5 个；推荐 5 个，但不是硬性要求 |
| `points[].glat/glon` | **GCJ-02**，与官方取点请求一致；地图底图是 AMap，点击得到的就是 GCJ |
| `points[].name` | 只用于界面与日志，不参与协议 |

### 4.2 选择策略

首版：**均匀随机，不避重**（`avoid_last=false`）。同一个锚点可以连续出现。

- 在 `on_start` 的确认框之前选好，并在确认框里显示：
  `本次取点位置：A3 教学楼（34.xxxxxx, 113.xxxxxx）`
- 选完写回 `last_used_id`，只用于日志和界面提示，**不排除**下次再次选中它。
- 记录一个 `selection_seed`（例如 `uuid4().hex`）到运行日志，便于回查“为什么这次选了 A3”。
- 锚点池只有 1 个点时，行为不变：每次都选它。
- 后续可加 `rotate`：按 `last_used_at` 最久未用优先，保证各锚点轮流出现；首版不做。

### 4.3 校验

保存时（编辑器）：

- 允许 **1–5 个点**；推荐 5 个，但少于 5 个也允许保存，界面只提示“推荐画满 5 个”。
- 至少 1 个点才能保存；0 个点视为未配置。
- `id` 唯一、`name` 非空。
- `glat/glon` 为有限数值，中国范围内（纬度 3–54、经度 73–136）。
- 用 OSM 校园边界做**近似**校验：点应在 `running/data/campus_<id>.json` 的 `boundary` 内；不在则警告并禁止保存。
- 可选警告：
  - 点落在建筑多边形内（`buildings`）——不是硬错误，因为学生可能站在建筑旁，但提示“取点位置在建筑内，建议移到道路上”；
  - 两个锚点距离 < 100 m——提示“太近，可能返回同一组点”。

运行时（协议侧）：

- 登录后拿到官方围栏，重新校验选中的锚点是否在围栏多边形内；不在则**不发取点请求**，直接失败并提示“锚点不在官方围栏内，请重新绘制”。
- 官方围栏可能与 OSM 边界略有差异（历史记录：官方 5 点有 4 个在围栏外，规划边界曾外扩 350 m），所以保存时的 OSM 校验只作近似，运行时以官方围栏为准。
- 如果学校有多个围栏/区域：选择包含锚点的围栏；首版目标学校只有一个“全校围栏”，可先按 `fences[0]` 处理，多区域留到 GAP-02 一起解决。

## 5. 取点链路

### 5.1 调用链

```text
一键跑步.pyw on_start()
  → 读取 anchor_points.json，选 anchor，写 last_used_id，显示在确认框
  → runner.run(config, anchor=anchor)
    → SportClient792.execute_run(anchor_gcj=(glat, glon))
      → RunningClient.execute_full_run(anchor_gcj=...)
        → policy.get_checkpoints_for_run(fence, uuid, rule, anchor_gcj=...)
          → get_run_checkpoints(rule.min_distance, anchor...) 
            → POST /api/v560/get/1/distance/{min_distance}
```

### 5.2 协议改动（只加可选参数）

| 文件 | 改动 |
| --- | --- |
| `policy/client.py` | `get_checkpoints_for_run(..., anchor_gcj=None)`；有锚点用锚点，没有则回退 `fence.polygon_points[0]`；记录 `last_checkpoint_anchor` |
| `policy/client.py` | `get_run_checkpoints(..., anchor_gcj=None)` 把锚点传给 `get_distance_route_points` |
| `policy/client.py` | `get_distance_route_points(..., latitude, longitude)` 已支持任意坐标，不需要改请求体 |
| `running/client.py` | `execute_full_run(..., anchor_gcj=None)`；传给 `get_checkpoints_for_run`；写日志 |
| `running/client.py` | `RouteContext` 增加 `anchor_gcj`、`anchor_id`、`anchor_name`，供 route provider 展示/记录 |
| `sport_client.py` | `execute_run(..., anchor_gcj=None)` 透传 |
| `running/models.py` | 新增 `RouteDecision`（见 §6.3） |

**不修改**：`builder.py`、`schema.py`、签名、OBS、结算、回查、轨迹采样。

### 5.3 请求字段

只改两个值：

```python
body = {
    "longitude": anchor.glon,      # 原来是 fence.polygon_points[0].gcj_coordinates()
    "latitude": anchor.glat,
    "selectedUnid": int(self.unid),
    "uuid": uuid_str or str(uuid.uuid4()),
    "runec": runec,
    "runAreaId": run_area_id,
    "sign": sign,
}
```

- `uuid` 仍每次运行新生成，不参与锚点选择。
- `sign` 是对 URL 的签名，不随锚点变化。
- `runAreaId` 仍是当前区域选择逻辑（本项目为 -1）。

### 5.4 回退

- 没有 `anchor_points.json`、文件为空、或所有锚点都无效 → 保持现有行为：用围栏第一个顶点，日志打 `[警告] 未配置有效锚点，回退围栏顶点`。
- 用户没有绘制锚点也能正常跑步，不阻塞旧流程。

## 6. 路线决策

### 6.1 命中路线库

沿用 `手动路线与路线库方案.md`：

- 用当次 5 点计算 `points_key`（`unid + area_id + 排序后的 GCJ 坐标`，5 位小数）；
- `find_by_points()` 只按 5 点位置匹配（EPS 5 m、顺序无关、同一命名空间）；
- 多个变体按长度装得下目标优先、圈数少、点位偏差小、最近使用排序；
- 命中后走现有“展开到目标距离 → 校验 → 提交”。

锚点不参与 `points_key`。同样的 5 点由哪个锚点取到，不影响路线复用。

### 6.2 未命中：三选一

未命中时，当前实现直接返回 `manual_route_missing`。方案改为在**不重新取点**的前提下让用户选择：

| 选项 | 行为 |
| --- | --- |
| **手动画线** | 打开现有 `RouteEditor`，传入当次 5 点；用户画完保存后继续提交 |
| **OSM 自动规划** | 用当次 5 点走现有官方排序（`select_official_order`）+ OSM 避建筑规划，直接生成路线 |
| **取消** | 不提交，结束本次运行；已经取到的点不落盘、不上传 |

对话框必须显示：

- 本次锚点：`A3 教学楼（34.xxxxxx, 113.xxxxxx）`
- 当次 5 点名称与顺序
- `points_key` 前 10 位
- “这不是错误：官方返回了一组路线库里没有的点位”

### 6.3 `route_provider` 契约扩展

现有契约（`running/client.py`）：

```python
provider(context) -> Optional[Tuple[polyline, ordered_checkpoints]]
# 返回 None = 手动模式未返回路线 → manual_route_missing
```

为了区分“取消”和“改用 OSM”，新增一个显式决策对象，保持旧返回值兼容：

```python
# running/models.py
from dataclasses import dataclass
from typing import Optional, List, Sequence

@dataclass
class RouteDecision:
    mode: str                      # "manual" | "osm" | "cancel"
    polyline: Optional[List[Sequence[float]]] = None
    ordered_checkpoints: Optional[List[dict]] = None

    @classmethod
    def manual(cls, polyline, ordered_checkpoints):
        return cls("manual", polyline=polyline, ordered_checkpoints=ordered_checkpoints)

    @classmethod
    def osm(cls):
        return cls("osm")

    @classmethod
    def cancel(cls):
        return cls("cancel")
```

兼容规则：

- 返回 `(polyline, ordered)` → 按手动处理（旧行为）；
- 返回 `None` → 取消/失败（旧行为，**不静默回退 OSM**）；
- 返回 `RouteDecision` → 按 `mode` 处理；
- `mode="osm"` 时，协议使用**同一组已取到的 checkpoints**，跳到现有 OSM 分支；不重新请求取点接口；
- `mode="cancel"` 时返回明确的失败信息，例如 `manual_route_cancelled: 用户取消本次提交`。

### 6.4 OSM 回退细节

- 复用 `select_official_order(checkpoints, day_goal, min_distance, sequence_strength, rng=random.Random(run_uuid))`；
- 复用现有 `running/osm` 规划器与 `validate_track()`；
- 失败时返回明确错误（例如 `osm_failed: ...`），不自动再请求一次点位；
- 可选增强（后续）：OSM 失败后再次询问用户“改手动画线 / 取消”，因为 checkpoints 还在内存里，不需要重新取点。

### 6.5 为什么不在 provider 外重新跑一次

- 会再次请求取点接口，消耗 3 次/5 分钟配额；
- 同一窗口内服务端可能返回同一组，也可能跨窗口返回另一组，导致“用户看到的是 A 组，实际提交的是 B 组”；
- 重新登录/重新取点还会延长一次真实提交的链路，增加失败面。

## 7. 桌面端交互

### 7.1 绘制锚点

首版建议新增独立窗口 `anchor_editor.py`，复用现有地图基础件：

- `route_editor.CampusMap`：校园边界、建筑、道路、`MapProjection`；

## 10. 错误与限流

| 场景 | 处理 |
| --- | --- |
| 没有锚点池 | 回退围栏顶点，日志警告，不阻塞 |
| 锚点不在官方围栏内 | 不发请求，失败：“锚点不在官方围栏内，请重新绘制” |
| 锚点池 1–4 个 | 正常使用；界面提示“推荐画满 5 个”，不阻塞 |
| 取点返回 `10603` | 失败：“5 分钟内最多取点 3 次，请等待后再试”；**不重试** |
| 取点网络超时/断连 | 失败并显示原因；**不自动重试**（避免消耗配额） |
| 返回点位不足 2 个 | 沿用现有失败文案，停止提交 |
| 返回点位缺少 `glat/glon` | 沿用现有失败文案，停止手动路线 |
| 路线库未命中 | 弹三选框；不静默回退 |
| OSM 规划失败 | 失败并显示原因；可选后续“改手动画线” |
| 用户取消 | 不提交，结束；不写 outbox |

## 11. 验证计划（只读，未来执行）

> 本节只描述实验，不在本次讨论中执行。

### 11.1 目的

确认两件事：

1. 官方是否按传入坐标**就近**返回 5 点；
2. 换锚点能否得到**不同**的 5 点集合。

### 11.2 前提

- 使用测试账号（证据链中的 `uid 15040628`），不要用主账号；
- 只调用规则、围栏、取点三个读接口；
- 不生成轨迹、不上传成绩；
- 一次登录，复用会话；
- 官方限制 5 分钟 3 次，严格按窗口安排。

### 11.3 实验步骤

| 步骤 | 操作 |
| --- | --- |
| 1 | 从已画锚点里挑 3 个**分散**的点（相距最远，例如操场、宿舍区、校门）；不足 3 个时补画或分两次实验 |
| 2 | 登录，取规则、围栏 |
| 3 | 第 1 个窗口：用锚点 A、B、C 各取一次点（正好 3 次） |
| 4 | 记录每次的 5 点坐标、名称、`points_key`、耗时、错误码 |
| 5 | 等待 5 分钟 |
| 6 | 第 2 个窗口：用同样的 A、B、C 再各取一次 |
| 7 | 计算：每个返回点到对应锚点的距离；不同锚点集合的交集/差集 |
| 8 | 把结果写入 `logs/anchor-probe-<时间>.json`（logs 已 gitignore），不放入仓库 |

### 11.4 判定

| 结果 | 解释 | 下一步 |
| --- | --- | --- |
| 同一窗口内 A/B/C 返回**不同**集合，且点集中在各自锚点附近 | 锚点有效 | 进入实现 |
| 同一窗口内 A/B/C 返回**同一**集合，跨窗口才变 | 锚点被忽略，随机只发生在时间维度 | 停止“换点”目标；锚点池只保留起点一致性/记录价值 |
| 两个窗口都完全一样 | 学校点位池固定 | 同上；与锚点无关 |
| 返回点距离锚点普遍 > 2 km | “就近”半径很大或未使用锚点 | 结合上一行判断 |

### 11.5 验收标准（建议）

- 至少 2 个锚点返回的集合存在差异（差 1 个点也算）；
- 至少 4/5 个返回点距离锚点 ≤ 1.5 km（阈值可按首次实测调整）；
- 第 4 次请求返回 `10603`，确认限流行为未被新代码绕过；
- 整个实验 0 次提交、0 次 OBS 写入。

## 12. 风险与开放问题

### 12.1 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 服务端忽略锚点 | 方案达不到“换位置换点”的目标 | §11 先验证；不成立就回退 |
| 锚点太少或太集中 | 返回同一组点，误判“方案无效” | 编辑器提示锚点间距；实验用分散点；推荐画满 5 个 |
| 新点集导致路线库频繁未命中 | 每次都要画线或 OSM | 三选一；OSM 作为兜底 |
| 锚点与轨迹起点不一致 | 用户已确认不强制；仍可能被服务端视为不合理 | 记录为已知风险，不额外限制；实测中观察是否影响结算 |
| OSM 数据只覆盖打包校园 | 锚点在校外/边界外时 OSM 失败 | 锚点必须在校内；OSM 失败明确报错 |
| 5 分钟 3 次 + 单设备保护 | 实验/调试成本高 | 测试账号；一次登录多次取点；不自动重试 |
| 锚点池含真实坐标 | 隐私/泄露 | `anchor_points.json` 加入 `.gitignore`；文档只用占位坐标 |
| 锚点位于建筑/水域 | 取点结果不合理或被判异常 | 编辑器用 OSM 建筑做警告 |
| 服务端返回的 5 点仍按时间轮换 | 即使锚点有效，短时间内也可能重复 | 接受；不强行“刷点” |

### 12.2 已确认

1. **路线起点不必等于锚点。** 用户确认不强制；轨迹起点与取点锚点可以不同，记录为已知风险（§12.1）。
2. **锚点池允许 1–5 个。** 推荐画满 5 个，少于 5 个也允许保存和运行。
3. **随机不避重。** `avoid_last=false`，允许连续两次选到同一个锚点。
4. **锚点写入路线库历史与运行日志。** 不写入官方提交报文。

### 12.3 待确认

1. **锚点选择在登录前还是登录后？**
   建议登录前（确认框可见、可取消、不消耗登录）；代价是随机种子与 `run_uuid` 无关，日志单独记录 seed。
2. **Android 端何时跟进？**
   当前只做桌面端；Android Vue3 尚未开始（M0）。锚点数据格式保持一致，后续可直接复用。
3. **如果服务端返回的 5 点与锚点无关，但仍会随时间变化，是否还保留锚点池？**
   建议保留：至少保留“本次从哪个位置取点”的记录，比固定围栏顶点更可追溯。
